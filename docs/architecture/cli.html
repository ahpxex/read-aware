命令行 ReadAware

一个没有 Agent 的无界面 ReadAware。桌面 app 开着或关着都能用，直接读写同一份书库、导入书籍，和 app 遵守同一套写入规则。

1. 目标与边界

  • 独立运行。app 没开也能用；app 开着时也是同一个 CLI、同一条路径，直接打开同一个 SQLite 数据库。不做"app 在线走 IPC、离线直连"两种模式。
  • 同一套写入规则。每次写入都是"追加事件 + 更新投影"在同一个事务里完成，和 app 完全一致。CLI 不直接改书架表，也不另写一份写入逻辑。
  • 这一期不做：Agent、模型和 API 密钥；同步推送（由 app 负责，CLI 写的事件进入同一个待推送队列）；移动端；阅读引擎相关功能（需要网页视图）；CLI 的安装与分发。

2. 为什么是纯 Rust

写入链路上最重的东西本来就在 Rust 里：写入与投影规则、数据库升级、文件存储、各格式的元数据和封面提取、封面压缩，存储层约 4.8 万行。这些代码对 Tauri 的依赖基本只在最外层很薄的命令包装上，可以原样拆出来，让 app 和 CLI 共用。

如果用 Bun 写 CLI，仍然得挂一个 Rust 子进程或动态库，就成了两个运行时、两套分发。用 Rust 写，产物是一个独立的可执行文件。

3. 代码结构

搬进共享存储包的

  • 打开数据库的全过程：数据库设置、自定义 SQL 函数（批注全文索引依赖它）、启动时的恢复检查、数据库升级、本机设备身份。
  • 事件写入与投影规则（apply.rs）以及它们依赖的模块。
  • 文件存储、书架读取、导入核心（算哈希、去重、复制、提取元数据和封面）。
  • 统一的错误类型 CommandError。

留在桌面端的

  • 所有 Tauri 命令包装；安卓文件路径处理、外部打开、封面图片协议；开机启动、文件关联这类系统副作用；插件、备份对话框、本机只读 API、API 密钥。

构建上要跟着改的

  • 编译目录从 apps/desktop/src-tauri/target 移到仓库根，发版流程里写死的产物路径、CI 缓存配置都要改。
  • 审计过的 auto-launch 补丁和几个依赖的优化等级必须搬到根配置。留在原地会被 Cargo 静默忽略。
  • 安卓和 iOS 构建要实测一遍，Tauri 2 早期版本在 workspace 下出过问题。
  • 删掉现在的 Bun 骨架，重新生成 bun.lock。

4. 只有一个导入实现

现在导入分两半：Rust 负责算哈希、复制文件、提取封面；"导入了一本书"这条事件由网页端的 TypeScript 组装并提交。CLI 如果在 Rust 里再写一遍，就成了两份实现，迟早会走偏。

设计：把整个导入收进共享存储包里的一个函数 import_book，从记录导入意图、判断格式、去重、复制、提取，到组装事件、提交，一气呵成。桌面 app 改为调用它，网页端只服务于导入的那部分 TypeScript 逻辑随之删除；CLI 直接调用同一个函数。

  • 极少数两边都得有的纯逻辑（例如从文件名推断书名和作者，元数据补全时也会用到），沿用项目里阅读进度规则的做法：一份共享的用例表，两种语言的测试都跑它，保证结果一致。
  • 导入函数和"补齐同步过来但缺文件的书"这条路径目前都没有直接测试，这次补上。

5. 两个进程共用一个库

现在的代码默认只有一个进程会打开数据库。CLI 要写入，以下五件事得先做完。

必须先修事件可能被静默丢掉

每条事件都带一个排序用的时钟戳，数据库规定同一台设备的戳不能重复。现在插入时遇到重复会悄悄跳过，界面仍显示成功，事件却没存下来。app 的时钟只在启动时校准一次，看不到 CLI 后来写的戳，而两者用的是同一个设备身份，所以两边真有可能撞上。

  • 区分两种"重复"：同一条事件被再次提交属于正常情况，照旧跳过；不同事件撞了同一个戳，就报错并整笔回滚。
  • app 收到这个错误，重新校准时钟、换新戳，再提交一次。
  • Rust 端自己生成戳的地方，都在独占写事务里先读最新戳再往后排。

进程锁

数据目录里放一把锁。app 和 CLI 打开书库时都持有共享锁。升级数据库、从备份恢复、清空数据、压缩数据库这几类大操作需要独占锁，拿不到就明确报"另一个 ReadAware 进程正在使用书库"，不会在别人写到一半时动手。

版本保护

书库版本appCLI
和程序一致正常打开正常打开
比程序旧拿到独占锁后升级拿到独占锁后升级；app 开着就提示先退出 app 或更新
比程序新拒绝打开，提示更新 app拒绝打开，提示更新 CLI

"比程序新"这一行目前没有任何保护，会静默继续运行。这次一并修掉。

导入一半的文件不被误删

app 启动时会清理"上次没导入完"的残留文件，判断标准是"不是我这个进程留下的"。如果 CLI 正在导入时 app 启动，CLI 的文件会被当成残留删掉。改为每个进程持有一把属于自己的锁，只清理锁已经释放（进程已退出或崩溃）的残留。

app 能看到 CLI 写进来的东西

现在 app 只在自己写完后刷新界面，CLI 导入一本书，开着的 app 不会显示。改为 app 每秒查一次 SQLite 自带的"别的连接是否提交过"计数器。这个计数器只在别的进程写入后才变，开销极小。一旦发现变化，app 走一遍同步拉取后的那套刷新（书架、对话、偏好），同时重新校准时钟，并尽快推送 CLI 新写的事件。

6. 元数据补全

有些格式要靠阅读引擎才能拿到书名、作者或封面：所有 PDF 的书名和作者、非 macOS 上的 PDF 封面、cbr 漫画。CLI 没有阅读引擎，只能等 app 打开时补。

  • 没问题封面：app 按数据库里记录的"封面待检查"状态挑书去补。
  • 有缺口书名和作者：app 只挑"书名仍等于文件名"的 PDF 去补，所以 cbr 漫画的元数据永远补不上，PDF 拿到书名但缺作者时也补不上。在 app 里导入时会当场补，这条规则只是兜底；而 CLI 导入的书每次都会落进这个缺口。

已确认：把"元数据待补"记进数据库

导入事件里加一个"元数据待补"标记（旧事件视为已补完，兼容同步），app 按这个标记挑书去补，补完提交一条结论清掉它。这样 CLI 导入和 app 导入的结果完全一样。随第 3 阶段（统一导入）一起做。

7. 数据目录与身份

  • 默认使用 app 的书库目录：macOS 是 ~/Library/Application Support/com.readaware.app，Windows 是 %APPDATA%\com.readaware.app，Linux 是 ~/.local/share/com.readaware.app。
  • --dev 指向开发版书库；--data-dir 或环境变量 READAWARE_DATA_DIR 可以指定任意目录。
  • 目录里没有书库时直接报错，不会因为路径打错就凭空建一份空书库。要新建，就显式运行 ra init。
  • CLI 使用和 app 相同的本机设备身份，它写的事件同步出去，和 app 写的没有区别。

8. 第一期命令

ra [--data-dir <路径> | --dev] [--json] [-v] <命令>

  books list            列出书架：书名、作者、格式、阅读进度、封面状态
  books show <id>       查看一本书的详情
  import <文件>...       导入一个或多个文件，逐个报告：新增 / 已存在 / 补齐文件 / 失败
  init                  在指定目录新建书库
  • 默认输出给人看；加 --json 输出固定结构，方便脚本处理，出错时带稳定的错误码。
  • 退出码：0 成功，1 运行出错（批量导入中有任何一个失败也算），2 参数用错。
  • 不会把程序内部的报错堆栈打给用户；加 -v 才输出诊断日志。

9. 实施阶段与验收

每个阶段单独提交，前一阶段验收通过再开始下一阶段。

  1. 拆出共享存储包，行为不变。三个平台的原生测试全过；桌面开发版、正式构建、安卓构建、iOS 构建都能跑通；发版产物路径核对无误。
  2. 打好两个进程共存的基础。第 5 节五件事全部落地，用"两个连接 / 两个进程"的测试覆盖：时钟冲突、锁、版本保护、导入残留归属。
  3. 统一导入。app 改用共享的导入函数，删掉重复的 TypeScript 逻辑，补上共享用例表和缺失的测试。
  4. CLI 第一期命令。第 8 节的四个命令，CI 里跑 CLI 测试。
  5. 在真实运行的 app 上验收。
    • app 关着时用 CLI 导入 epub 和 pdf，再打开 app，书架、封面、PDF 元数据都齐全；
    • app 开着时用 CLI 导入，一两秒内书架上出现新书，之后在 app 里导入、做批注都正常；
    • CLI 导入过程中在 app 里点恢复备份，app 明确提示书库被占用，数据无损；
    • 开着同步时，CLI 导入的书能同步到另一台设备。

10. 已确认的决定

  1. 元数据补全：把"元数据待补"记进数据库。
  2. 命令名是 ra，提供 init。
  3. 分发方式等功能做完再定。在此之前只保证在仓库里能运行。
