全局错误处理审计与统一化方案

逐层扫描了错误的产生（Rust/IPC、AI、异步管线）、传播（分类与映射）和呈现（inline、toast、dialog、boundary）。 结论：捕获层扎实，分类层几乎不存在，呈现层碎成了十一种各自为政的写法。统一化完全可行，方案按四层给出。

日期 2026-08-30 范围 apps/web · apps/desktop · packages/agent · plugins 方法 三路并行静态扫描（呈现面 / 吞错误 / 基础设施）

这不是「补几个 catch」的问题，而是中间缺了一整层：错误从产生地（Rust 命令、AI provider、后台管线）到呈现地（toast、行内文案、错误屏）之间，没有任何统一的分类与映射。 于是每个呈现点只能二选一——要么把 error.message 原样丢给用户（14 处），要么干脆不说（8 处用户该知情却沉默的位置，含 1 条真实的数据丢失路径）。

好消息是地基已经打好：日志接缝（logger.ts）、滚动文件日志、诊断包、双层 error boundary、全局 unhandledrejection 捕获都在且质量不错。 要补的是中间的「错误词表 + 单一映射函数」，再把呈现收敛到三种（toast / 行内 / 表单字段），改造是收敛式的而非推倒重来。

Section 01现状：好的部分，先说清楚

统一化不是从零开始。这些设施已经在位，方案会直接依赖它们：

  • 日志接缝：apps/web/src/platform/logger.ts 的 createLogger(module)，info/warn/error 同时进 console 与 Tauri 滚动文件日志（4×5MB），92 个调用点、26 个模块标签。日志里「只放 id 与错误文本、不放用户内容」的约定写在文件头。
  • 全局兜底：global-error-log.ts 捕 window.error 与 unhandledrejection；boot-failure.ts 处理启动失败（纯 DOM，不依赖可能已挂掉的 React/i18n）；Rust 侧 install_panic_log_hook 记 panic 与 backtrace。
  • 双层 boundary：路由根部 RootErrorBoundary + 四个 FeatureErrorBoundary（reader / agent / stats / plugin-page），带 resetKey 与重试。
  • 诊断包：日志尾部 + 投影完整性自检，导出或自愿上报（/v1/report），一切出设备的动作都经用户确认。
  • 两个模范样本：DataSyncPanel.tsx:49 明确注释「raw 进日志、用户看本地化文案」；useLibraryController.ts:77 的 reportError 是「log 原因 + toast 摘要」的正确形状——但它们都只是局部习惯，没升级成全局设施。
  • 表单字段错误：TextField / Select / TextArea 的 error prop（含 aria-describedby）是全应用唯一真正一致的错误呈现，各处文案也都本地化了。保持不动。

Section 02病灶一：吞错误

数据丢失路径：旧会话导入失败被当成成功，随后删除源数据

P0

desktop-import.ts:163 里 importKvConversationsIntoSqlite 遇到 JSON.parse 失败会静默 return——形同成功；调用方 local-store.ts:166 紧接着 delete_kv 删掉旧数据。一个损坏的 legacy blob 意味着 v6 之前的全部聊天记录被永久删除，无日志、无提示。同目录的姊妹迁移（interim-projections.ts:84/128）都做对了：失败时记日志并保留原 key 等待重试。

读失败被渲染成「空」，与「没有数据」不可区分

P1

数据库锁死、迁移失败、FTS 出错时，这些界面显示的是一个看起来很正常的空列表或 0：

  • useBookAnnotations.ts:24 — 标注列表 catch → []
  • useAnnotationCounts.ts:59 — 统计页全部归零
  • AnnotationsPopover.tsx:24 — 全局标注浮层
  • useBookMarks.ts:29 — 完读页书签列表
  • system-fonts.ts:29 — 字体列表变空、usePluginFieldOptions.ts:82 — 插件下拉变空

写失败无提示：用户以为保存了，其实没有

P1
  • useReaderTextActions.ts:235/324/344/462 — 高亮、改色、删除、笔记保存失败只进日志，笔记内容直接丢弃。这是与 library 层 reportError 最刺眼的不一致。
  • local-store.ts:76/88、secret-store.ts:74-111 — KV / API key / 同步主密钥落盘失败，但内存快照已更新：界面显示已保存，重启后消失。
  • ReaderCompletionScreenView.tsx:108 — 标记完读失败，开关静默弹回。

packages/agent 的 memory 管线整层无日志

P1

thread.ts 已有可选注入的 deps.log，但 memory/*（extraction、consolidation、rolling-summary、narrativity、graph-upkeep）全部 catch → 空值。最隐蔽的是 graph-upkeep.ts：tick 失败返回 0，digestBookCatchUp 把 0 理解成「backlog 清完了」直接停手——一本书的图谱可能永远建不起来，且无任何痕迹。

Section 03病灶二：没价值的 diagnose 信息直达用户

根因在传播层的两处结构塌缩，14 个呈现点只是下游症状：

  1. IPC 边界：131 个 Tauri 命令全部 Result<T, String>，零错误枚举。rejected invoke() 抛出的是裸 string 而非 Error 实例——前端遍地的 err instanceof Error ? err.message : String(err) 对 IPC 失败全部走后一个分支，且调用方只能靠子串匹配区分「文件不存在」和「磁盘满」。
  2. AI 边界：packages/agent/src/runtime/thread.ts:645 把 provider 失败重新包成 new Error(errorMessage)——HTTP 状态、错误类型、可重试性在这一行全部丢失。整个 AI 栈只有一个错误码（ai-not-configured）；429 限流、401 鉴权失败与网络抖动不可区分，重试按钮对永久性错误也照样出现。

Section 04病灶三：呈现碎片化

同类错误在不同 feature 里长成了 11 种样子。仅红色就用了三档（red-600/700/800）；同一个同步失败在三处渲染成三种完全不同的组件；AI 聊天有全应用最好的错误卡（错误码 → 本地化文案 → 行内修复链接 → 重试），却是私有组件，别处用不上。

Dialog 的答案：现状恰好是对的。全仓库 13 个 Dialog 全是确认、表单和内容查看，没有一处用 modal 弹错误——这符合产品的编辑式克制，应升格为明文规则：错误不打断（不用 Dialog / window.alert），例外只有启动失败与根 boundary 这两个「整个应用已不可用」的场景。

Section 05统一化方案：四层

第一层 · 错误分类：AppError + 稳定错误码词表

地基

新建 apps/web/src/platform/errors.ts（词表类型放 packages/core 供 agent 包共享）：

  • AppError 基类：code（稳定字符串，如 db/locked、fs/not-found、ai/rate-limited、sync/quota-full）、retryable、cause。现有 10 个孤立 Error 子类（RelayError、WrongPassphraseError…）归入该基类，各自领一个 code。
  • IPC 包装：唯一入口 invokeIpc() 替换 199 处裸 invoke()，把裸 string 拒绝统一包成 IpcError extends AppError——一次性根治「rejected invoke 不是 Error」的类型陷阱。
  • Rust 侧分两步：先在高失败价值的域（library 导入、annotations、sync、secrets）引入 thiserror 枚举、serde 序列化为 { code, message }，invokeIpc 识别该形状还原成带码的 IpcError；其余命令保持 String、落入 ipc/unknown，随后按域渐进迁移。131 个命令一次全改不划算也不必要——码只在「UI 需要区分处理」时才有价值。
  • AI 层：在 thread.ts:645 结构塌缩点就地分类（限流 / 鉴权 / 网络 / 上下文超限 / 终态），扩充 ai-errors.ts 现成的码表机制；重试按钮只对 retryable 出现，鉴权失败改为「打开设置」链接（该交互 ChatMessageError 已实现，只差码）。

第二层 · 消息映射：唯一的 describeError()

核心

describeError(error, t) → { title, body, retryable, action? }：有码走本地化码表；无码给通用文案、raw 只进文件日志。以下全部删除并改走它：4 个重复的私有 errorMessage()、formatLibraryError、formatReaderError。铁律：raw error.message 永不进 JSX，诊断细节的唯一去处是文件日志与诊断包（boundary fallback 提供「复制详情 / 打开日志目录」替代当前的 mono 直出）。

第三层 · 呈现收敛：三种 surface，一条禁令

UI
  • Toast（操作失败）：给 ToastOptions 加 action 槽（Alert 已有先例），失败一律 destructive——修掉插件桥的 default variant。用于保存 / 导入 / 同步这类「动作没成」。
  • InlineError（面内错误，新组件进 @read-aware/ui）：以 ChatMessageError 为蓝本、基于 Alert 实现：role="alert"、标题 + 本地化正文 + 可选重试 / 修复链接，统一一档红。替换 11 种写法里的 3–7、9、10：行内红 span、Caption 手搓、reader 错误屏（并给 FoliateReaderView:2281 补上重试 + 返回书架的出口）、boundary fallback、更新指示器。
  • 表单 error prop：已一致，保持。
  • 禁令：Dialog 不用于错误。写进规则，现状已满足。

第四层 · 规则固化（CLAUDE.md + 本文档）

防回潮
  1. raw 错误文本永不给用户；用户看 describeError，日志看 raw。
  2. catch 三选一：注明 best-effort 理由 / 记日志 / 上报 UI——不存在第四种。
  3. 读失败 ≠ 空状态：加载失败必须渲染 InlineError，不许 catch → []。
  4. 写失败必须让用户知道（toast），且不得先改内存快照后落盘失败装无事。
  5. 后台管线（memory / digest / 插件任务）必须持有注入的 logger。
