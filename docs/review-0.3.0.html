第一节P0 · 插件沙箱

已修复

插件移出主 realm，权限成为真正的边界

已实证

过去插件通过 await import() 直接进入应用 realm，因而持有应用的全部权限。 现在每个插件运行在独立的 module Worker 里（plugin-sandbox.worker.ts）， 那里没有 window、没有 document、没有 __TAURI_INTERNALS__。 唯一的出口是 postMessage，而宿主侧（plugin-worker-host.ts）只把消息路由到 buildPluginContext —— 也就是原来那份权限门禁。区别在于它现在是唯一的通道。

同一段攻击探针，改动前后

// 模拟一个声明零权限的插件
                     改动前              现在
__TAURI_INTERNALS__  可达                undefined
library_load         OK  22 books        BLOCKED (TypeError)
load_kv_all          OK  25 keys         BLOCKED
read_events_since    OK  1222 events     BLOCKED
annotations_list     OK  15              BLOCKED
plugin_docs_list     OK  6 docs（他人的）  BLOCKED
localStorage         可读（含 API key）   undefined
document / window    可达                undefined
主 realm 插件模块      直接 import         0 个

两个设计要点

  • 插件源码不需要改。 storage.get() 和 dictionary.getLanguage() 在插件 API 里是同步的， 现在依然同步——宿主在 activate() 前把整个命名空间快照送进 Worker，读取始终是本地的。 跨 realm 的只有宿主与 Worker 之间。
  • 上下文形状从宿主自动派生，不手抄。 第一版我手写了一份 API 列表，结果漏了 books.write 是嵌套命名空间，导致 rss-reader 的自检失败。现在宿主用 describeContext() 把真实 ctx 的形状发给 Worker，Worker 据此构造代理—— 沙箱暴露的永远正好是权限门禁授予的，不多不少。

功能验证（三个内置插件，零错误）

rss-reader       激活  → 3 agent tools（books:write 自检通过）

  → [{0,8}, {8,17}, {17,22}]   往返 6ms

连带的 API 变更（仅影响宿主，不影响插件作者）： RegisteredReaderMode.segmentText 现在可能返回 Promise。分段每章执行一次并缓存， 所以每次翻页不产生额外开销；useTextUnitNavigator 相应加了 generation 守卫， 防止慢分段把上一章的结果画到当前页上。

第二节P0 · 密钥不再明文

已修复

API key 离开 localStorage，改为加密存储

上一版指出原注释的推理是反的——"因为是密钥所以不放 SQLite"，而 localStorage 恰恰是唯一没有任何门禁的地方。 现在密钥经 AES-256-GCM 加密后存入 SQLite，密钥文件单独放在数据库旁边、权限 0600。 旧值在首次启动时自动迁移，且只有加密写入成功后才清除本地副本。

app_kv 中的存储值                    104 字符密文，不含明文片段
secret.key                          -rw------- (0600)
启动时钥匙串弹窗                      0

为什么不用系统钥匙串

第一版实现走的是 OS 钥匙串，但那条路被否掉了，理由是一个不成立的前提： "用户授权一次就好"依赖稳定的代码签名，而本项目没有—— codesign 对 dev 和 release 构建都报 adhoc、无 team identifier。 macOS 的钥匙串 ACL 绑定二进制签名，因此每次重新编译、每次发版更新都会被当成新应用重新索要授权。 每次启动弹一次授权框不是安全特性，是在训练用户闭眼点确认。

这个取舍成立的前提是威胁模型已经变了：让旧 localStorage 危险的是"任何插件都能读"， 而插件现在根本不在有存储访问权的 realm 里运行（第一节）。剩下的威胁是"以该用户身份运行的本地进程"， 钥匙串对它的优势真实但狭窄，却要用每一次启动的打扰来换。

诚实标注这买到了什么： 它能阻止密钥以可读明文躺在磁盘上——备份、同步文件夹、数据库截图、随手 grep 都拿不到， 单独拖走 read-aware.db 只得到密文。 它不能阻止一个已经以该用户身份运行的进程同时读走两个文件——只有 OS 钥匙串或硬件密钥能做到。 等应用具备 Developer ID 签名后应当重新评估：那时钥匙串只弹一次，就变成严格更优解。

过程中修掉的一个真问题

第一版把 secret_get 写成了同步 Tauri 命令。macOS 首次访问钥匙串会弹授权框， 而同步命令跑在主线程上——整个 webview 直接冻结，连最简单的 eval 都超时。 用 sample 抓主线程栈定位到阻塞点后，改为 async + spawn_blocking。 同一类问题也修了 rebuild_projections / verify_projections， 它们会回放整个日志，绝不能占用主线程。

阅读时长：一次不可省略的历史补全

自检立刻发现一个真实风险：reading_time_daily 有 621 行，而回放只产生 0 行—— 旧的 fire-and-forget 从没把 timeRecorded 写进日志。也就是说，那时候执行 rebuild_projections 会清空用户全部阅读统计。

聚合无法反推出原始的每一次记录，但可以重建出产生同样表内容的分布：把每本书的日、时两个边缘分布 相乘成联合网格，再用运输问题的可行解构造分配舍入余数，使两个边缘都精确复原。 

reading_time_genesis  → 合成 12,417 条事件
阅读统计               → totals / daily / hourly 一字未变
三张表的漂移            621 / 146 / 12 行  →  0

补全按差额计算：日志里原本已有 4 条真实的 timeRecorded，直接合成全量会把它们算两遍。 Rust 测试 reading_time_genesis_tops_up_around_events_already_in_the_log 专门钉住这条。

第四节仍然存在的边界

已知

历史数据里有无法挽回的事件缺失

自检目前仍报告漂移。逐条定位后，全部是旧双写路径留下的痕迹，与新代码无关：

表live / replay原因
annotations4 / 3重新上色的 highlight.recolored 当年丢了，回放只剩创建事件
books8 / 8时间戳差 1ms（旧前端与 HLC 取值时机不同）

这些不该靠伪造历史抹平。它们会自然收敛：任何一行被新路径重写后就脱离漂移集—— 本次验证中打开一本书触发进度更新，books 的漂移当场从 9 对降到 8 对。

设计上就不参与回放的两类数据（已在 DIFF_SPECS 显式建模）： 书籍封面（从对象存储内容本地提取，重建时保留，不强制重新提取全部书籍）； 对话的 parts_json / error（渲染结构与失败占位，是呈现状态而非对话事实）。 把它们纳入比较只会让自检永远误报。

第六节对上一版报告的更正

上一版第四节写的"7 对 feature 循环依赖"，术语用错了。

我当时统计的是目录级双向耦合——feature A 里某个文件 import 了 B，同时 B 里另一个文件 import 了 A。 这不构成 import 环：两条路径经过的是不同模块。用 madge 做真正的模块级检测， 全仓当时只有 2 个真循环（就是上面修掉的那两个）。

结论本身仍然成立——双向耦合确实意味着 feature 无法被单独理解、测试、替换， reader ⇄ plugins（5/28）这样的耦合度也确实偏高。但"循环依赖"有严格的技术含义， 用它来描述双向耦合会夸大问题的性质。这一点是我的错误。

第七节审计之后

这份审计交付后，同一批代码上又做了两件事。记在这里，因为其中一件暴露了审计本身的验证盲区。

新增

读完一本书有了终点

此前读到最后一页只是翻不动了：状态只能从 progressPercent >= 100 推断，没有地方看单本书的阅读代价， 留下的标注也只能在阅读中从笔记面板翻。现在读者主动越过最后一页会进入一屏完成界面， 带三样东西：他自己的「读完」判断（新增 book.finished 事件，且是粘性的—— 到 100% 不等于承诺，多翻一页也不算撤销）、这本书花掉的时间、以及他留下的标记。

「回顾这本书」不在这一屏渲染，而是把问题交给 agent：它自己调 get_annotations / get_book_overview 取材，答案落在本书已有的对话线程里，读者可以追问—— 这三点都是内联的一次性调用做不到的。

末尾判定：两次错误的方向

第一版用 relocate 上报的全书进度 ≥ 0.999 判断读完。那个事件只在位置变化时触发， 到末尾恰好静默，而恢复到末尾的会话从未收到过它——症状就是一直翻页毫无反应。 第二版改成数 relocate 次数加 420ms 延时推断「没动」，能工作，但那是在猜渲染器已经知道的事。 最终直接问引擎：foliate 的 atEnd 表示后面没有 linear section，分页与滚动模式语义一致； 但它容许差两页（服务于滚动预留），所以用它把关「后面还有没有」，精度交给 page/pages 比较。

已修复

沙箱边界曾丢弃 contribution 的可调用方法

审计的盲区

第一节报告插件沙箱验证通过时，检查的是「三个插件激活、贡献出现在注册表里」。 那还不够：跨 Worker 时 contribution 要拆成可克隆的数据加留在 Worker 的函数句柄， 而当时用一份手写清单决定哪些属性是函数——它是契约的第二份副本，且已经与之不符。 tool 的可调用字段是 execute 不是 run，header action 是 view， 两者被静默丢弃：5 个插件 agent 工具全部注册成功但无法调用。 

agent 自己报出了症状：
"the dictionary plugin won't load right now"
  → get_vocabulary 在注册表里，但没有 execute

修法不是补齐清单，而是删掉它——连宿主侧那份必须与之对应的 switch 一起。 函数改为在 RPC 层通用传递：参数被递归遍历，任何位置任何名字的函数都换成句柄，宿主再还原。 没有任何地方枚举 contribution 种类，也就没有东西能和契约脱节。 顺带解决了注册方法同步返回 PluginDisposable 这个跨 realm 做不到的事—— 现在每次调用返回的东西既可 await 也可 dispose。

教训：验证 registration 类功能要验「可调用」，不只是「注册项出现在列表里」。 这与第六节那处术语错误同源——都是没验的那一侧恰好是坏的那一侧。 本次收尾的端到端验证也正是靠这条抓到了另一个问题：ask 类标注（agent 为线程内提问留下的被动痕迹） 出现在了完成屏的「你的标注」里，等于把读者自己的回顾指令记成了他标注的段落。
